## 1. 개요

동행복권 로또 6/45 당첨 결과를 웹에서 수집하고, 데이터베이스에 저장한 뒤, 통계 분석 결과를 Streamlit 웹 화면에서 차트와 그래프로 보여 주는 프로젝트다.

한 흐름으로 **데이터 파이프라인 + 분석 + 대시보드**를 보여 주는 것이 핵심 산출물이다. 당첨을 예측하거나 번호를 추천하는 서비스가 아니다.

### 1.1 배경

- 로또 6/45는 1~45 중 6개 + 보너스 1개를 추첨한다.
- 회차·추첨일·당첨번호·등수별 당첨 정보는 공식 사이트에 공개되어 있다.
- 단순 조회를 넘어, **이력 전체를 모아 분포·추이를 한 화면에서 설명**하는 데모가 포트폴리오에 적합하다.

### 1.2 제품 목표

1. 1회부터 최신 회차까지 당첨 결과를 재현 가능하게 수집한다.
2. 수집 데이터를 SQLite에 저장하고, 이후 실행 시 신규 회차만 추가한다.
3. 번호 빈도, 핫/콜드, 홀짝·합계, 연속·번호쌍, 보너스, 당첨금 추이, 회차별 조회를 제공한다.
4. Streamlit 대시보드에서 위 분석 결과를 차트로 시연한다.

### 1.3 성공 기준

아래를 모두 만족하면 Part 1~3 초안 목표가 달성된 것으로 본다.

- 로컬에서 `.venv`로 수집 → 분석 → 대시보드를 순서대로 실행할 수 있다.
- DB에 1회부터 최신 회차까지 공백 없이 적재되어 있다 (실패한 회차는 로그로 남기고 재시도 가능).
- 각 회차에 당첨번호 6개, 보너스, 1~5등 당첨자 수·당첨금이 있다.
- 합의한 분석 7종이 대시보드에서 확인된다.
- 화면과 README에 **데이터 출처(동행복권)** 와 **통계는 당첨을 보장하지 않음** 고지가 있다.
- 리뷰어가 README만 보고 데모를 재실행할 수 있다.

## 4. 3단계 로드맵

```text
Part 1 수집  →  Part 2 분석  →  Part 3 시각화
   |                |                |
 원본 웹        SQLite/pandas     Streamlit
  → SQLite         통계 산출        차트·조회
```

각 Part는 이전 Part의 산출물을 입력으로 쓴다. Part 3만 실행해도 DB가 있으면 데모가 되어야 한다.

### Part 1. 데이터 수집

- 최신 회차 확인
- 1회~최신 회차 수집
- SQLite 적재
- 증분 갱신 (이미 있는 회차는 건너뜀)
- 수집 로그와 실패 회차 재시도

**Part 1 완료 조건:** DB에 전체 회차가 들어가고, 같은 스크립트를 다시 돌리면 신규 회차만 추가된다.

### Part 2. 데이터 분석

- pandas로 SQLite를 읽어 통계를 계산한다.
- 분석은 재사용 가능한 함수/모듈로 두고, 대시보드와 CLI에서 같이 쓴다.
- 분석 결과는 화면에서 바로 계산하거나, 필요 시 요약 테이블로 저장한다. 초안에서는 **조회 시점 계산**을 기본으로 한다.

**Part 2 완료 조건:** 합의된 7종 통계가 입력 기간(전체 또는 최근 N회)에 대해 숫자로 산출된다.

### Part 3. 데이터 시각화

- Streamlit 멀티페이지
- 차트: 막대, 히트맵, 선, 분포
- 회차 조회·검색
- 출처·면책 문구

**Part 3 완료 조건:** 로컬에서 대시보드를 열고 7종 분석과 회차 조회를 시연할 수 있다.

## 6. 데이터 요구사항

### 6.1 소스 (제안)

1순위는 동행복권 공식 사이트 `dhlottery.co.kr`이다. 비공식 통계 사이트는 주 소스로 쓰지 않는다.

권장 수집 방법:

1. **공식 JSON 회차 조회**  
   회차 번호를 넣어 당첨번호 6개, 보너스, 추첨일, 1등 관련 금액을 받는다. 구조화되어 HTML 파싱보다 깨질 위험이 적다.
2. **공식 회차별 결과 HTML**  
   JSON에 2~5등 당첨자 수·당첨금이 없으면 같은 회차의 공식 결과 페이지를 보조로 파싱한다.
3. **최신 회차**  
   공식 최신 결과 페이지 또는 JSON 성공 응답으로 확인한다. 존재하지 않는 회차는 수집을 멈춘다.

HTML만으로 전부 긁는 방식은 백업으로 둔다. 페이지 구조가 바뀌면 Part 1이 깨지므로, JSON을 우선한다.

### 6.2 저장 필드 (논리 모델)

코드가 아니라 의미 모델이다. 구현 시 테이블을 나누어도 된다.

**회차 (draw)**

- 회차 번호 (정수, 고유)
- 추첨일
- 본번호 1~6 (오름차순 저장 권장)
- 보너스 번호
- 총 판매금액 (공식 제공 시)
- 수집 시각
- 출처 (json / html / mixed)

**등수별 당첨 (prize)**

- 회차 번호
- 등수 (1~5)
- 당첨자 수
- 등수별 1인 당첨금 (또는 해당 등수 총 당첨금 — 공식 표기와 일치시킬 것)
- 필요 시 배출 게임 수 등 부가 필드

품질 규칙:

- 본번호는 1~45, 서로 중복 없음, 정확히 6개
- 보너스는 1~45, 본번호와 중복 없음
- 등수는 1~5, 회차당 5행
- 당첨자 수 0 이상, 금액 0 이상
- 회차 번호는 1 이상 연속. 빈 회차가 있으면 실패 목록으로 남긴다

### 6.3 갱신 정책 (제안)

포트폴리오에 맞게 **수동 실행 + 증분 추가**를 기본으로 한다.

- 실행 시 DB 최대 회차와 공식 최신 회차를 비교한다.
- 없는 회차만 요청한다.
- 로또 추첨은 토요일 밤이므로, **일요일 이후 주 1회 수동 실행**으로 최신 상태를 유지한다.
- OS 크론/작업 스케줄러는 README에 “선택”으로만 안내한다. Part 1 필수가 아니다.
- 전체 재수집은 스키마 변경이나 데이터 손상 시에만 사용한다.

### 6.4 데이터 고지

- 원본 저작·공개: 동행복권
- 본 프로젝트는 개인 학습·포트폴리오 목적의 재가공이다
- 과거 출현 빈도는 미래 당첨을 의미하지 않는다

### 8.1 스택

- 언어: Python 3.x
- 가상환경: 프로젝트 루트 `.venv`
- 수집: `requests` 또는 `httpx`. HTML 보조 파싱 시 BeautifulSoup
- 저장: SQLite (파일 DB, 별도 서버 없음 — 포트폴리오·로컬 데모에 적합)
- 분석: pandas
- 시각화: **Streamlit** (Dash는 사용하지 않음. 이후 검토 항목)
- 차트: Streamlit 기본 차트 + Plotly 또는 Altair. 히트맵·인터랙션이 필요한 화면에 사용
- 의존성: `requirements.txt`로 고정

### 8.2 디렉터리 안내 (초안)

실제 폴더명은 구현 착수 시 맞춰도 된다. 역할만 구분한다.

- `docs/` — PRD 등 문서
- 수집 스크립트 — 원본 → SQLite
- 분석 모듈 — DB → 통계
- Streamlit 앱 — 페이지별 화면
- `data/` 또는 동등 위치 — SQLite 파일 (대용량 바이너리는 git 정책에서 별도 결정)

### 8.3 Streamlit 화면 구성 (제안)

| 페이지 | 내용 |
| --- | --- |
| 소개 | 프로젝트 목적, 데이터 기간, 출처, 면책 |
| 회차 조회 | 회차 검색, 번호 검색, 해당 회차 당첨금 |
| 번호 빈도 | 막대 + 히트맵, 본번호/보너스 포함 토글 |
| 핫·콜드 | 최근 N회 슬라이더 |
| 분포 | 홀짝, 합계, 연속번호 |
| 번호쌍 | 상위 동시 출현 쌍 |
| 당첨금 추이 | 등수 선택, 당첨자 수 / 금액 |

사이드바에 DB 회차 범위와 “데이터 갱신은 수집 스크립트 실행” 안내를 둔다.

## 9. 제약, 리스크, 가정

### 9.1 가정

- 수집 대상은 동행복권 로또 6/45 공식 공개 데이터다.
- 사용자는 로컬에서 Python을 실행할 수 있다.
- 포트폴리오 시연은 작성자 PC 또는 녹화/스크린샷으로 충분하다. 클라우드 배포는 필수가 아니다.
- 번호 예측은 제품 목표가 아니다.

### 9.2 제약

- 공식 사이트 HTML/JSON 변경 시 수집이 실패할 수 있다.
- 요청을 너무 빠르게 보내면 차단되거나 예의가 아니다.
- 당첨금 표기(세전/세후, 1인 금액 vs 등수 총액)는 공식 표기를 따르고, 화면에 어떤 값인지 밝힌다.
- 2등 이하는 JSON에 없을 수 있어 HTML 파싱 의존이 생긴다.

### 9.3 리스크와 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 공식 JSON/HTML 구조 변경 | 수집 중단 | 파서를 회차 조회와 HTML로 분리. 실패 회차 로그 |
| 초기 전체 수집 시간 | 데모 준비 지연 | 간격 유지 + 재개 가능한 증분 저장 |
| 번호쌍 조합 계산량 | 대시보드 지연 | 상위 K개만, 또는 기간 필터 |
| “예측 도구”로 오해 | 포트폴리오 메시지 왜곡 | 면책 문구, 예측 기능 미구현 |
| SQLite 파일을 git에 넣음 | 저장소 비대 | gitignore 여부는 구현 시 결정, README에 수집 후 생성된다고 명시 |

### 9.4 규정·윤리

- 개인·포트폴리오·학습 목적의 공개 데이터 이용
- 공식 이용약관·robots.txt를 확인한 뒤 수집 간격을 지킨다
- 당첨 보장·투자 권유가 아님을 UI와 README에 명시한다
